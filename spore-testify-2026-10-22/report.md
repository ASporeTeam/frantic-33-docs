## 1. Why this library, and who this is for

Testify is the assertion library that most of the Go ecosystem has already standardised on: 26,000+
stars, a fresh upstream push within the last week of the reference build, five public packages
(`assert`, `require`, `mock`, `suite`, `http`), and a MIT licence that lets anybody read, vendor and
redistribute it.

That makes it a good subject for a per-symbol reference, and it makes the reference useful to a
large audience: every Go developer who has written `assert.Equal` has had to answer the same
three questions — *which package do I need*, *is there a chainable or a package-level form*, and
*what does this assertion actually guarantee*. Upstream answers none of them in a single place.

## 3. The gaps this reference closes

### 3.1 The example gap is the big one

The public API exports **714** entry points. Upstream ships **9** runnable `Example…` functions for
all of them, and all nine are attached to the five `…AssertionFunc` types (`ComparisonAssertionFunc`,
`ValueAssertionFunc`, `BoolAssertionFunc`, `ErrorAssertionFunc`, `PanicAssertionFunc`) in `assert`
and `require`. There is not one runnable example for `mock`, `suite` or `http`, and none for the
`…f` variants that make up roughly half of `assert` and `require`.

A developer asking "how do I assert that a mock was called with a specific value" has nothing to
copy from the repository. This reference puts every one of those entry points on one searchable
page with its signature, its upstream doc comment, and a link to the exact upstream line — and the
[coverage page](https://testify.anonymux.org/coverage) states the example count so the gap
is visible rather than implied.

### 3.2 The three-way duplication is invisible in the README

Testify's surface is deliberately redundant, and the redundancy is the first thing that confuses
new users:

- `assert.Equal` (package-level, returns `bool`) vs `require.Equal` (package-level, calls
  `t.FailNow()`) vs `(&assert.Assertions{}).Equal` (chainable, on `*Assertions`).
- Each of those has an `…f` twin with a format string, so `assert.Equal` and `assert.Equalf` are
  two of the 158 package-level functions in `assert` alone.

Upstream explains the difference in prose. This reference shows all three forms side by side for
each concept, with the exact method list (152 chainable methods on `*Assertions`, 158 package-level
functions in `assert`, 153 in `require`), so the choice is a lookup instead of a memory test.

### 3.3 One entry point instead of five silos

`pkg.go.dev` gives you one package at a time. A real task — "assert on a mock's call, then set up
a suite, then check the HTTP body" — crosses three packages. This reference publishes a single
index of all 711 documented entries across the five packages, with full-text search, and every page
is also available as Markdown and through `llms.txt` for tooling and language models.

### 3.4 Every link is pinned to a commit

Every source link on the site points at
`https://github.com/stretchr/testify/blob/87a7b9d57689f6579db2da795ab8deeab29cb724/<file>#L<line>`.
Nothing points at a moving branch. A reader can prove that the signature they are looking at was
the upstream signature at a stated commit, and the reference can be rebuilt and diffed against a
later state of the library.

## 5. Limitations — what this reference does **not** do

Stated plainly, because a reference that oversells itself is worse than none:

1. **It adds nothing upstream.** No commit, issue or pull request was made to the Testify
   repository. This is a read-only reference over an existing tree.
2. **It does not fix the example gap.** It measures it and makes the surface navigable; it does not
   author the 700 missing examples. The upstream pull requests that would close that gap are
   still worth writing, and this reference is a ready-made inventory of which symbols need one.
3. **Exported surface only.** The `godoc` adapter documents exported declarations. Internal
   packages (`internal/spew`, `internal/difflib`, `assert/internal/unsafetests`) are excluded by
   design; they are not public API and not part of the audience for this reference.
4. **It is a snapshot, not a live mirror.** It describes one commit and does not track `master`.
   Rebuilding it against a newer commit is one command (below) but is not automatic.
5. **No interactive playground.** Every example on the site is upstream's own text; nothing here is
   executed in the browser, so the reference cannot be used to try an assertion out.
6. **The four undocumented symbols are listed, not documented.** `mock.Anything` and the two
   `argumentMatcher` methods appear because they are exported and useful, but they carry no
   upstream prose.

## 6. Reproducing this, cheaply

The reference is a pure function of (a) the pinned upstream commit and (b) one committed snapshot
file. A third party can rebuild and re-verify it without a Go toolchain:

- `npm install sourcey@3.8.3` — the generator, from the public npm registry.
- `sourcey build -c sourcey.config.ts -o dist` — rebuild the site in snapshot mode; no Go toolchain needed.
- `sourcey godoc -m . -p "./assert,./require,./mock,./suite,./http" --exclude "github.com/stretchr/testify/internal" -o godoc.json` — regenerate the snapshot (needs Go).
- Serve `dist/` and compare it against <https://testify.anonymux.org/>; the pages are byte-stable for the same snapshot.
- Download <https://testify.anonymux.org/packet/evidence.json> and re-run each observation's `method` against its `url`.
- Download <https://testify.anonymux.org/packet/receipt.json> and run `runx verify --receipt <path>` to re-check the sealed run.

With the Go toolchain present, the snapshot itself is regenerated with:

```bash
sourcey godoc -m . \
  -p "./assert,./require,./mock,./suite,./http" \
  --exclude "github.com/stretchr/testify/internal" \
  -o godoc.json
```

For the Testify project specifically, the natural next step would be to run exactly that command
in CI on every commit and publish the result under a domain the project controls, so the reference
tracks `master` while every individual page stays pinned to the commit it was built from. That is
the one thing a maintainer could adopt from this work.

Concrete steps we would recommend to the project, in order of value per unit of effort:

- Commit the `godoc.json` snapshot to a CI job that runs `sourcey godoc` on every release tag, so the reference can never drift from the tree it describes.
- Use the measured coverage table as the work list for doc comments: only 4 exported symbols are undocumented, so the remaining work is examples, not prose.
- Open upstream issues for the packages with zero runnable examples (`mock`, `suite`, `http`), starting from the exported symbols this reference lists per package.
- Publish the generated site under a domain the project controls (a documentation subdomain of the project's own site), so readers see it as part of Testify rather than as a third-party mirror.
- Keep every page pinned to a commit, exactly as this reference does, so quotes in bug reports stay reproducible.
